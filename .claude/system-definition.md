# KUKA FM Middleware – System Definition

Specification (**what** to build) for all agents. Read it fully before any change.
If something here conflicts with code, this file wins – raise the conflict to the user.
How to work (agents, workflow, rules, architecture) is defined only in `CLAUDE.md`.

---

## 1. Purpose and scope

- **Current state:** KUKA AMR Fleet Manager (KUKA FM) runs standalone; operators dispatch and watch missions directly in its UI.
- **Goal:** a middleware that simplifies and unifies access to KUKA FM through its own REST API and web UI:
  - dispatch a mission (RACK_MOVE only),
  - force-cancel a running mission,
  - periodically sync mission and robot states from KUKA FM into its own PostgreSQL DB, keeping full history,
  - web UI with missions and robots (current + historical states), polling every 1 s.

### In scope (FR)
| ID | Requirement |
|---|---|
| FR1 | Dispatch mission → KUKA `submitMission` |
| FR2 | Cancel mission → KUKA `missionCancel` (FORCE only) |
| FR3 | Poll mission states via KUKA `jobQuery`, store in DB |
| FR4 | Poll robot states via KUKA `robotQuery`, store in DB |
| FR5 | Keep full history of mission and robot states |
| FR6 | Web UI: missions with current + historical states |
| FR7 | Web UI: robots with current + historical states |

### Non-functional
| ID | Requirement | Decision |
|---|---|---|
| NFR1 | Containerized, persistent DB | Docker Compose, PostgreSQL with volume |
| NFR2 | Own API protected | **Out of scope.** No auth on middleware API, no users/roles. Protection exists only on KUKA FM side. |
| NFR3 | KUKA FM `Authorization` token | Token is supplied via config (`appsettings.Production.json` generated by CD). Token validation is done by KUKA FM – not our scope. |
| NFR4 | Structured logs | Serilog → Seq |
| NFR5 | CI/CD | Azure DevOps YAML pipelines on a local Windows agent |

### Explicitly out of scope
- `missionStateCallback` (KUKA → middleware callbacks) – impossible because of reverse proxy. Use polling only.
- Mission types other than `RACK_MOVE`.
- Cancel modes other than `FORCE`.
- pause / recover / resume (`operationFeedback`) / retry.
- Tracking missions not dispatched by the middleware.
- Authentication, users, roles on middleware side.
- Integration and E2E tests. Frontend tests.

## 4. KUKA FM integration

- **Base URL:** `https://kukafm.its.fei` (from `appsettings`; same real KUKA FM for development and production). Host name resolved via the host's hosts file (works inside Docker Desktop containers).
- **TLS:** KUKA FM uses a **self-signed** certificate (`CN=its.fei`, SAN `*.its.fei`). Its public part `docker/certs/kukafm.crt` is added to the API image trust store. Never commit private keys (`*.pfx`, `*.key`).
- **All endpoints:** `POST {BaseUrl}/interfaces/api/amr/{apiName}`
- **Headers:** `Content-Type: application/json`, `Authorization: {accessToken}` (raw token value from config, as in KUKA docs).
- **Never log the token.**
- Source doc: `KUKA_AMR_Fleet_2.15_en-API.pdf`, chapter 7.

### Response envelope (all endpoints)
```json
{ "data": ..., "code": "0", "message": null, "success": true }
```
`success=false` → error. Treat as failure, log `code` + `message`, surface to caller.
Common error codes: 100001 unexpected, 100002 invalid parameter, 100404 required param missing, 100013 enum not exists, 100204 no such node, 100301 robot/robot type not exists, 100408 request ID duplicate, 100409 mission code duplicate.

### 4.1 `submitMission` (UC1)
Request (fields from user input in **bold**, rest from `appsettings`):
```json
{
  "orgId": "<config>",
  "requestId": "<generated, max 32>",
  "missionCode": "<generated, max 32>",
  "missionType": "RACK_MOVE",
  "viewBoardType": "<config>",
  "robotModels": "<config>",
  "robotIds": ["<robot.robot_code of selected robot>"],
  "robotType": "<config, e.g. LIFT>",
  "priority": <user 1–99>,
  "containerModelCode": "<config>",
  "containerCode": "<user>",
  "templateCode": "",
  "lockRobotAfterFinish": <config>,
  "unlockRobotId": "",
  "unlockMissionCode": "",
  "idleNode": "<config>",
  "missionData": [
    { "sequence": 1, "position": "<user start node>",  "type": "NODE_POINT", "actionType": "UP_CONTAINER",   "passStrategy": "AUTO", "waitingMillis": 0 },
    { "sequence": 2, "position": "<user target node>", "type": "NODE_POINT", "actionType": "DOWN_CONTAINER", "passStrategy": "AUTO", "waitingMillis": 0 }
  ]
}
```
Node `type`, `actionType`, `passStrategy`, `waitingMillis` are config defaults.

`missionCode` and `requestId` are generated by the middleware: **max 32 characters, unique** (enforced by UK constraints in DB; KUKA also rejects duplicates with 100408/100409). A new `requestId` is generated for every KUKA call that needs one.

### 4.2 `missionCancel` (UC2)
```json
{ "requestId": "<generated>", "missionCode": "<mission.mission_code>", "containerCode": "", "position": "", "cancelMode": "FORCE", "reason": "" }
```

### 4.3 `jobQuery` (UC5)
- Called **once per sync tick** (not per mission). `limit` and other filters (`sourceValue`, `createUsername`, `maps`, …) from config.
- Response `data[]`: `jobCode` (= our `mission_code`), `status`, `robotId`, `workflowId`, `targetCellCode`, `beginCellCode`, `createTime`, `completeTime`, `warnFlag`, `warnCode`, …
- Match results to tracked active missions by `jobCode`. Unknown `jobCode`s are ignored.
- **Fallback:** for every tracked active mission missing in that response (outside the `limit` window), call `jobQuery` with `jobCode` = its `mission_code`.

**Job status codes**
| Code | Name | Class |
|---|---|---|
| 10 | Created | active |
| 20 | Executing | active |
| 25 | Waiting | active |
| 28 | Cancelling | active |
| 50 | Warning | active |
| 30 | Complete | final |
| 31 | Cancelled | final |
| 35 | Manual complete | final |
| 60 | Startup error | final |

### 4.4 `robotQuery` (UC8)
- Request `{}` – always all robots, **no filters**.
- Only status codes 1–7 are sent by KUKA. `batteryLevel` is a percentage 0–100. Values always fit the column lengths in §6.
- Response `data[]`: `robotId` (= our `robot_code`), `robotType`, `mapCode`, `floorNumber`, `buildingCode`, `containerCode`, `status`, `occupyStatus`, `batteryLevel`, `nodeCode`, `x`, `y`, `robotOrientation`, `missionCode`, …

**Robot status codes and mapped state** (mapping is done **in code**, not stored)
| Code | Name | Mapped state |
|---|---|---|
| 1 | Departure | Busy |
| 2 | Offline | Offline |
| 3 | Idle | Available |
| 4 | Executing | Busy |
| 5 | Charging | Busy |
| 6 | Updating | Busy |
| 7 | Abnormal | Offline |

## 5. Business rules

### Startup and sync order
1. On startup **robot sync runs first**. Mission sync starts only after the first robot sync that **succeeds and returns at least one robot** (until then mission sync waits; robot sync keeps retrying on its interval).
2. Both syncs then run on their own interval from config.
3. A KUKA error in a sync is logged; nothing is written; retry on next tick.

### UC1 – Dispatch mission
- Input: `robotId` (required, must exist in `robot` table), `startNode`, `targetNode`, `containerCode`, `priority` (1–99). All required.
- Validate → call `submitMission` → only on success insert `mission` with status 10 / Created.
- On KUKA error: return error to UI, log it, **do not** store the mission.

### UC2 – Cancel mission
- Mission must exist (404) and be active (10, 20, 25, 28, 50) else 409.
- Call `missionCancel` with `FORCE`. Do not change status locally – final status (31) comes from mission sync.

### UC5 – Mission sync
- Load tracked missions with active status → one `jobQuery` (+ per-`jobCode` fallback for missing ones, §4.3) → for each matched mission whose data changed:
  1. insert previous state into `mission_status_history` (`valid_from` = previous `updated_at`, `valid_to` = now),
  2. update `status`, `status_name`, `robot_id` (if KUKA reports a different robot that exists in DB), `updated_at`,
  3. set `completed_at` when status becomes final.
- Final missions are not polled anymore.

### UC8 – Robot sync
- One `robotQuery` → for each robot:
  - unknown `robot_code` → insert,
  - **any** changed column (incl. `robot_type`) → insert previous state into `robot_status_history`, then update,
  - robots missing from the response → left unchanged (no history),
  - DB error during a tick → handled like a KUKA error (logged, nothing written, retry next tick).
  - invalid data from KUKA (e.g. status code outside 1–7) → **no fallback**: the whole tick fails (logged, nothing written). Until a robot sync succeeds, mission sync never starts – failures cascade by design.
  - a failed KUKA call is logged twice on purpose: Warning by the KUKA client, Error by the sync.

### History rule
**Every change** of a mission or robot creates one history row holding the **previous** state.

### Logging (Seq)
- Every user operation (dispatch, cancel) with mission code, robot, result.
- Every KUKA call: api name, duration, success/code/message (never the token).
- Sync ticks: counts of changed/inserted rows, errors.

## 6. Data model (PostgreSQL)

Source: `documentation/erd.drawio`. All ids `bigint` identity. Timestamps `timestamptz` (UTC). snake_case via `EFCore.NamingConventions`.

- **Nullability:** columns are NOT NULL except those marked `NULL` below (values KUKA may not return, `robot.mission_code` / `robot_status_history.mission_code`, `mission.completed_at`). `mission.mission_code` is NOT NULL.
- **FK delete behaviour:** `Restrict` on all FKs – referenced robots/missions can never be deleted while used (no cascade delete of history).

### `robot`
| Column | Type | Key / note |
|---|---|---|
| id | bigint | PK |
| robot_code | varchar(32) | UK, KUKA `robotId` |
| robot_type | varchar(32) NULL | |
| status | smallint | KUKA 1–7 |
| status_name | varchar(32) NULL | |
| battery_level | numeric(5,2) NULL | % |
| map_code | varchar(32) NULL | |
| node_code | varchar(64) NULL | |
| mission_code | varchar(32) NULL | plain text, no FK |
| updated_at | timestamptz | |

### `robot_status_history`
| Column | Type | Key / note |
|---|---|---|
| id | bigint | PK |
| robot_id | bigint NOT NULL | FK → robot.id |
| robot_code, robot_type, status, status_name, battery_level, map_code, node_code, mission_code | as in `robot` (same types and nullability, no UK) | previous values – **mirrors every `robot` column** except `id`, `updated_at` |
| valid_from | timestamptz | |
| valid_to | timestamptz | |

### `mission`
| Column | Type | Key / note |
|---|---|---|
| id | bigint | PK |
| mission_code | varchar(32) | UK, KUKA `missionCode` / `jobCode` |
| request_id | varchar(32) | UK |
| mission_type | varchar(20) | `RACK_MOVE` |
| start_node | varchar(64) | |
| target_node | varchar(64) | |
| container_code | varchar(64) | |
| priority | smallint | 1–99 |
| robot_id | bigint NOT NULL | FK → robot.id |
| status | smallint | KUKA 10–60 |
| status_name | varchar(32) NULL | |
| created_at | timestamptz | |
| updated_at | timestamptz | |
| completed_at | timestamptz NULL | |

### `mission_status_history`
| Column | Type | Key / note |
|---|---|---|
| id | bigint | PK |
| mission_id | bigint NOT NULL | FK → mission.id |
| robot_id | bigint NOT NULL | FK → robot.id |
| mission_code, request_id, mission_type, start_node, target_node, container_code, priority, status, status_name, created_at, completed_at | as in `mission` (same types and nullability, no UK) | previous values – **mirrors every `mission` column** except `id`, `updated_at` |
| valid_from | timestamptz | |
| valid_to | timestamptz | |

**History rule for the schema:** a history table always mirrors every column of its parent table (except `id`; `updated_at` becomes `valid_from`). Adding a column to `robot`/`mission` requires adding it to its history table too.

Relations: robot 1–0..* mission · robot 1–0..* robot_status_history · robot 1–0..* mission_status_history · mission 1–0..* mission_status_history.

## 7. Middleware REST API

Base path `/api` (reachable only through nginx). JSON, camelCase. Errors as RFC 7807 ProblemDetails. No authentication.

| Method | Path | Purpose | Responses |
|---|---|---|---|
| GET | `/api/missions?state=active\|finished` | List missions (no `state` = all) | 200 |
| GET | `/api/missions/{missionCode}/history` | Previous states of a mission | 200, 404 |
| POST | `/api/missions` | Dispatch (UC1) | 201, 400 validation, 502 KUKA error |
| POST | `/api/missions/{missionCode}/cancel` | Force cancel (UC2) | 200, 404, 409 not active, 502 KUKA error |
| GET | `/api/robots` | List robots incl. mapped `state` | 200 |
| GET | `/api/robots/{id}/history` | Previous states of a robot | 200, 404 |
| GET | `/api/health` | Liveness for smoke check | 200 |

Dispatch body:
```json
{ "robotId": 1, "startNode": "M001-A001-45", "targetNode": "M001-A001-40", "containerCode": "1000002", "priority": 1 }
```

Mission DTO: `id, missionCode, missionType, startNode, targetNode, containerCode, priority, robotId, robotCode, status, statusName, isActive, createdAt, updatedAt, completedAt`.
Robot DTO: `id, robotCode, robotType, status, statusName, state (Available|Busy|Offline), batteryLevel, mapCode, nodeCode, missionCode, updatedAt`.
Robot history DTO: `robotCode, robotType, status, statusName, state, batteryLevel, mapCode, nodeCode, missionCode, validFrom, validTo` – newest first, **max 50 rows** per robot.
Mission history DTO: all mirrored columns (+ `robotCode`) + `validFrom`, `validTo` (defined in phase 6).

## 9. Configuration

- `ASPNETCORE_ENVIRONMENT`: `Development` locally, `Production` in CD deployment.
- `appsettings.json` – defaults below, **no credentials** (`ConnectionStrings:Default` empty, `AccessToken` empty).
- `appsettings.Development.json` – dev DB connection: `Host=postgres;Port=5432;Database=kukafm;Username=root;Password=password;GSS Encryption Mode=Disable`.
- DB authentication is **username/password only** – no Kerberos/GSSAPI. Every connection string sets `GSS Encryption Mode=Disable`.
- `appsettings.Production.json` – created by backend-expert, committed **with placeholders only** (`__DB_USER__`, `__DB_PASSWORD__`, `__KUKA_ACCESS_TOKEN__`, …). CD replaces them with secret pipeline variables using **jq** before any docker command; images are built only during deployment, so real values never reach the repo.
- Options classes are added in the phases that use them (not during scaffolding).

```json
{
  "ConnectionStrings": { "Default": "" },
  "KukaFm": {
    "BaseUrl": "https://kukafm.its.fei",
```

- `docker compose` **always builds** images (`docker compose build` / `up --build`).
- Docker Desktop with **Linux containers** on the Windows agent host.

## 11. Testing policy

- **Unit tests only**, backend only: xUnit + NSubstitute, plain `Assert`. **No FluentAssertions**, no integration/E2E tests, no frontend tests.
- Design backend for testability: depend on interfaces (e.g. KUKA client, repositories, clock) so they can be substituted.
- Must cover: input validation, KUKA request mapping, KUKA error handling, active/final status logic, robot state mapping, sync change detection and history creation.
- **Edge cases first**, e.g.:
  - validation boundaries: priority 0 / 1 / 99 / 100, empty / whitespace / too-long node and container codes, unknown robot id;
  - KUKA: `success=false`, error codes, timeout / HTTP failure, empty `data`;
  - cancel: unknown mission (404), each final status (409), already `Cancelling` (28);
  - mission sync: no change, status change, transition to each final status, unknown `jobCode`, mission outside `limit` window (fallback), robot id not in DB;
  - robot sync: new robot, unchanged robot, single-column change, every status code 1–7 mapped correctly.
- One behaviour per test; no tests for trivial getters/DTOs or framework code.
